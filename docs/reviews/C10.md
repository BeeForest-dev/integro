# C10 — models.organization

## Contract
```
Purpose:    org (tenant) row: id, name, slug, plan, created_at.
In -> Out:  persisted row, id uuid.
Errors:     duplicate slug -> unique violation mapped to 409.
Side fx:    table `organizations`.
Deps:       sqlalchemy.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/models/organization.py` defines `Organization(Base)` — id (`sa.Uuid`, primary key, `default=uuid4`), name (not null), slug (not null, unique, indexed), plan (not null, default `"free"`), created_at (timezone-aware `DateTime`, `server_default=func.now()`). `backend/app/repositories/organizations.py` adds `create_organization(session, name, slug, plan="free")` which flushes the row and maps an `IntegrityError` on the slug unique index to `AppError` with status 409 (C03). Migration `0002_organizations` (autogenerated, hand-checked) creates/drops the table.
2. Why it is built this way: `create_organization` flushes but does not commit — the caller owns the transaction boundary (C12 will own the unit of work); on the unique violation the session is rolled back first, because a session in an aborted transaction cannot serve anything else; `AppError` (C03) gives the 409 problem-details response for free at the API edge later. SQLAlchemy's `unique=True, index=True` collapses into exactly one unique index on slug (verified by reflection) — no redundant duplicate index.
3. How it is structured internally: model in `app/models` (imported from `app/models/__init__.py` so `Base.metadata` sees it), `alembic/env.py` gains `import app.models  # noqa: F401` so autogenerate diffs against the ORM; repositories layer starts with `organizations.py`; migration generated with `alembic revision --autogenerate` against a real PostgreSQL 16 and verified: upgrade head creates the table, downgrade base drops it, re-upgrade is clean (`alembic current` -> `b8a3131b3c7e (head)`).
4. Where the traps / failure modes are: the PG tests must never share an engine across `asyncio.run` loops — pooled asyncpg connections stay bound to their loop, so each test creates, uses and disposes its engine inside one coroutine (this exact bug surfaced during development and is documented in the test fixture); without `DATABASE_URL` the tests fail loudly with `RuntimeError` — there are deliberately no skips (verified: unset DSN -> all 4 fail); the autogenerated migration's `created_at` line exceeds the 100-char lint limit and is hand-wrapped; `env.py` import order was fixed per isort (`import app.models` before `from app.db.base import Base`).
5. How to verify it: start a real PostgreSQL (e.g. `docker run -e POSTGRES_USER=integro -e POSTGRES_PASSWORD=integro -e POSTGRES_DB=integro -p 55436:5432 postgres:16-alpine`), set `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:55436/integro`, then from `backend/`: `ruff check .` -> clean, `mypy app --warn-unused-ignores` -> clean (20 files), `pytest` -> **49 passed** (45 previous + 4 new: migration up/down/re-up, persist with uuid id + defaults, duplicate slug -> AppError 409, unique slug index via reflection). Proven real: without `DATABASE_URL` all 4 new tests FAIL; the migration up/down/re-up was also run manually via the alembic CLI on the same database (exit 0 each way). In CI the C08 workflow already provides the postgres service container, so no workflow change was needed.
