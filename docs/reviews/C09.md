# C09 — api.request_context

## Contract
```
Purpose:    middleware that assigns a correlation id to every request/response.
In -> Out:  request carries `x-request-id`; response echoes it; log lines include it.
Errors:     incoming id that is not a valid uuid -> generate a new one.
Side fx:    writes to the log context.
Deps:       fastapi, structlog.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/api/middleware.py` provides `RequestContextMiddleware` — a pure ASGI middleware that assigns one correlation id per HTTP request: a valid incoming `x-request-id` is reused (echoed back in canonical form), a missing or invalid one is replaced with a fresh uuid4. The id is bound into the structlog context (C02 `bind_correlation_id`) for the duration of the request, echoed on the response via a `send` wrapper, and cleared in a `finally` block. Registered in `create_app()` via `app.add_middleware`.
2. Why it is built this way: a pure ASGI middleware (no `BaseHTTPMiddleware`) keeps the request on one event-loop task without the threading/anyio bridge, so the structlog contextvars binding is exactly the context the route code runs in; the echo is implemented by intercepting `http.response.start` — one place that covers every response the app produces; `finally` guarantees cleanup even if the endpoint raises (the C03 exception handlers answer from inside the app, so the echo wrapper still sees the response start).
3. How it is structured internally: `_resolve_request_id()` (validate-or-generate, canonical string form), `RequestContextMiddleware.__call__` (skips non-HTTP scopes, binds, delegates, clears), `_echo_request_id()` (staticmethod wrapping `send` to append the header). One module-level constant for the header name. No state, no configuration.
4. Where the traps / failure modes are: header values are bytes — decode with strict ASCII before uuid parsing (garbage bytes fall through to a new uuid, never a 500); `MutableHeaders(raw=...)` requires a list copy, otherwise the ASGI message dict keeps a stale reference; only `http.response.start` gets the header — mutating body messages would corrupt the stream; httpx itself logs at INFO through the root logger once `setup_logging()` runs, so the log test filters to JSON lines instead of assuming every captured line is a log record; contextvars must be cleared in `finally`, not after a successful send, or an exception path leaks the id into the next request (test asserts the context is empty afterwards).
5. How to verify it: a clean venv installed strictly from `backend/requirements.txt`: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (16 files), `pytest` -> 45 passed (39 previous + 6 new: missing header -> generated uuid, valid header reused, invalid header replaced, correlation id present in the emitted log record, context cleared after the request, `create_app` registers the middleware).
