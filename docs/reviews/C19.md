## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: migration `0008_audit_log_full` extends `audit_log` with `entity`, `entity_id`, `before_json`, `after_json`, `ip` (all nullable — C15 rows stay valid); `record_audit` now accepts the full keyword-only field set (still strict, flush-not-commit, caller-built before/after — no diff magic); the new `try_record_audit` wraps the insert in `session.begin_nested()` and converts any failure into a structlog `audit_write_failed` event (action/entity/org ids only — never payloads) plus a `None` return; the two C15 call sites (`services/auth/registration.py`, `services/auth/login.py`) now use `try_record_audit` so a broken audit write cannot break register/login.
2. Why it is built this way: strict and isolated are two separate functions on purpose — `record_audit` aborts the caller on failure (audit-critical paths), `try_record_audit` is the failure-isolated wrapper (business-critical paths); the SAVEPOINT contains the failed insert so the caller's transaction survives a foreign-key violation or any other audit failure; payloads are excluded from the failure log because audit diffs may contain connection secrets.
3. How it is structured internally: `record_audit(session, *, organization_id, action, actor_user_id=None, entity=None, entity_id=None, before=None, after=None, ip=None)` and `try_record_audit(..., log=None)` in `app/services/audit.py`; the wrapper reuses the strict writer inside `session.begin_nested()`; the logger is an overridable parameter (defaults to the module structlog logger).
4. Where the traps / failure modes are: the forced-failure test uses a bogus `organization_id` (FK violation) — the strongest realistic failure; without the SAVEPOINT the failed insert poisons the session and the caller's commit dies with it (mutation 1); without the try/except the FK error propagates out of the wrapper (mutation 2); the test-suite lesson from C18 is applied here too — this module's fixture cleans before AND after every scenario so leftover audit rows cannot break other suites' organization cleanup through the foreign keys.
5. How to verify it: `docker compose up -d postgres`, `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:5432/integro`, from `backend/`: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (38 files), `pytest` -> **131 passed** on a freshly recreated database (127 previous + 4 audit tests: 0008 reflection + migration cycle, full-field roundtrip incl. JSONB diffs, `try_record_audit` happy path, forced FK failure -> None + caller insert commits + log has `audit_write_failed` and no payload keys). Mutation self-checks (both required): begin_nested replaced by a plain call -> isolation test FAILS; try/except removed -> isolation test FAILS; restored -> suite green.
