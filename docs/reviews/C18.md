# C18 — models.connection + repositories.connections

## Contract
```
Purpose:    CRUD for integration connections (type, config JSONB, encrypted secrets, status).
In -> Out:  connection row; secrets are never returned by the API, only `has_secret: true`.
Errors:     unknown type -> validation error with the list of supported types;
            decryption failure on read -> connection marked `secret_error`, not a 500.
Side fx:    table `connections`.
Deps:       core.crypto, repositories.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/models/connection.py` defines `Connection` (id, organization_id FK, name, type, config JSONB default {}, secret_ciphertext nullable, status default "active", created_at) with `SUPPORTED_TYPES = {"webhook_in", "telegram", "imap_mailbox", "http_api"}`; migration `0007_connections` creates the table. `backend/app/repositories/connections.py` is OrgScope-first: `create_connection` (validates the type with the supported list, encrypts the plaintext secret via C17 at rest, stamps the row with the scope's org), `list_connections`/`get_connection` (all reads through OrgScope — dogfooding C12), `read_secret` (decrypts; on CryptoError persists `status="secret_error"` and returns None — never a 500; a good decrypt self-heals back to "active"), and `to_api_dict` (exposes `has_secret` only — never the ciphertext).
2. Why it is built this way: the type is validated in the repository create — the single choke point — so no row with an unknown connector family can reach the database; the org id comes from the OrgScope, never from the caller; secrets exist in this module only as ciphertext outside `read_secret`, and the API-facing dict exposes a boolean — the M4 UI can show "has secret" without ever touching material; a wrong key degrades the connection (visible `secret_error` status) instead of crashing the pipeline, and one good decrypt restores it.
3. How it is structured internally: model + frozenset in `app/models`; repository functions take `(session, scope, ...)` with the app secret as an explicit parameter; `read_secret` owns the status state machine (`active` -> `secret_error` -> `active`). No API endpoints (out of contract; connector UI is M4).
4. Where the traps / failure modes are: `to_api_dict` must never include `secret_ciphertext` (the leak test stringifies the whole payload); JSONB round-trip is proven against the raw column via `text()`; the wrong-secret test stores the row under one key and reads with another; a test-suite trap fixed here: leftover `connections` rows break other PG suites' `Organization` cleanup through the FK — this module's fixture now cleans before AND after every scenario, and the full suite was re-verified on a freshly recreated database in CI order (127 passed).
5. How to verify it: `docker compose up -d postgres`, `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:5432/integro`, from `backend/`: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (38 files), `pytest` -> **127 passed** (119 previous + 8 new: migration cycle, create with JSONB + secret encrypted at rest, unknown type -> ValueError with the list, to_api_dict leak-free, org A/B isolation through OrgScope, read_secret happy path, wrong key -> secret_error persisted + None without raising, self-heal after a good decrypt). Mutation self-checks (both required): type validation removed -> unknown-type test FAILS; secret_error marking removed -> wrong-secret test FAILS; restored -> suite green on a fresh database.
