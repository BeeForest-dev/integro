# C22 — connectors.triggers.webhook (+ events storage, C23 delivered here)

## Contract
```
Purpose:    accept an inbound event via HTTP and normalise it.
In -> Out:  Event(id, org, type, payload, received_at).
Errors:     bad HMAC signature -> 401; unknown/inactive token -> 404;
            malformed JSON -> 400 with the offending field.
Side fx:    inserts `events`; enqueues a run.
Deps:       fastapi, services.events.
```

**Scope decision (reviewer, recorded in LOOP.md):** the events storage layer
(contract C23's content — model, migration, repository, idempotent
`store_event`) is implemented inside C22, because the endpoint cannot work
without it. C23 will be closed by the reviewer as "delivered inside C22".

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `app/models/event.py` + migration `0010_events` store inbound events with `UNIQUE(organization_id, idempotency_key)`; `repositories/events.py` (`insert_event`, `get_by_org_key`) and `services/events.py` (`store_event` -> `(Event, created)`; an IntegrityError re-fetches the existing row and returns `created=False` — a duplicate never creates a second row). `app/api/webhooks.py` exposes `POST /hooks/{connection_id}` (mounted in create_app, no auth): the connection resolves on the raw session, unknown/inactive/secret-less all answer the same uniform 404; `X-Webhook-Signature` = hex(hmac-sha256 over the RAW body bytes) checked with `hmac.compare_digest`, missing/bad -> 401; the body parses as a JSON object (400 with the decoder's msg/line/column otherwise); the idempotency key is the `X-Idempotency-Key` header or the sha256 of the raw body; on `created` the endpoint dispatches `app.workers.tasks.process_event` via a lazy-import seam and answers 202 `{event_id, received_at, duplicate}`. The placeholder task (the one allowed C07 touch) logs and returns the event id.
2. Why it is built this way: signing the RAW body means a re-serialized JSON with reordered keys still verifies (a parsed-then-reserialized HMAC would break real senders); the uniform 404 prevents existence probing for connections and secrets; dedupe lives on a database unique index — correct under concurrency, no application-level locking; the Celery app is imported LAZILY inside the enqueue seam because it reads `REDIS_URL` at import time and `app.main` must stay importable without env (importing the web module pulled celery into collection of every api test — caught by the full suite and fixed structurally).
3. How it is structured internally: model/repository/service layering as everywhere; the endpoint orchestrates verify -> parse -> store -> commit -> enqueue; `store_event` owns the duplicate semantics (rollback + re-fetch); the response shape carries `duplicate` so callers can tell a replay from a new event.
4. Where the traps / failure modes are: **celery 5.6 fact — `Celery.send_task` ignores `task_always_eager` (raises `AlwaysEagerIgnored`)**, so "eager" enqueue assertions must spy on the endpoint's enqueue seam and run the task body via `.apply(...)` where execution is verified; a `!=` swap for `compare_digest` does NOT fail the tampered test (both reject a modified body — the difference is the timing side channel), only removing the check does — the honest mutation for the self-check; the idempotency-header test proves two different bodies under one key dedupe to the first event.
5. How to verify it: `docker compose up -d postgres`, `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:5432/integro`, from `backend/`: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (47 files), `pytest` -> **181 passed** on a freshly recreated database (169 previous + 12 webhook tests: happy 202 + row + enqueue args + `.apply` result, bad signature 401, tampered body 401, unknown 404, inactive 404, no-secret 404, malformed JSON 400 with decoder detail, JSON array 400, replay -> duplicate:true + one row + one enqueue, idempotency header honored, re-signed re-serialized body verifies). Mutation self-checks (both required): signature check removed -> tampered/bad-signature tests FAIL; dedupe path removed -> duplicate test FAILS; restored -> suite green.
