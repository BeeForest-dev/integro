# C25 — connectors.triggers.telegram

## Contract
```
Purpose:    receive bot updates and normalise them into events.
In -> Out:  Event with type telegram.message, chat id, text, user id.
Errors:     wrong secret token header -> 401; update older than the last processed
            update_id -> ignored (no duplicate event); non-text message -> ignored with a log.
Side fx:    inserts `events`, enqueues a run.
Deps:       fastapi, httpx.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `app/api/telegram_webhook.py` exposes `POST /hooks/telegram/{connection_id}` (public ingress mounted in `create_app`): the connection resolves on the raw session (unknown/inactive/secret-less -> uniform 404); the `X-Telegram-Bot-Api-Secret-Token` header is checked against the connection secret (C18 `read_secret`) with `isascii()` BEFORE `hmac.compare_digest` (the C22 lesson), bad/absent -> 401. A text message normalizes to an event of type `telegram.message` with payload `{update_id, chat_id, user_id, text, message_id}`; the answer is always 200 `{"ok": true, "ignored": bool}` — Telegram only needs the 200.
2. Why it is built this way: dedupe is two-layered — the C22 idempotency index (`telegram:{connection_id}:{update_id}`) kills exact replays, and `connection.config["last_update_id"]` rejects anything older than the last seen id, so an old id never seen by this connection cannot create an event; the config update commits in the same transaction as the event; non-text updates (photos, stickers, service messages, bare callback_query) are acknowledged with `ignored: true` and a structlog `telegram_update_ignored` entry (update_id + reason) — no event, no idempotency row; enqueue goes through the same lazy `_enqueue` seam as C22, after the commit, only when an event was created.
3. How it is structured internally: one router module mirroring the C22 layout (`get_settings`, uniform error helpers, `_extract_message`, `_ignored`); `store_event` from C22/C23 owns idempotency; the worker pipeline is untouched — this trigger only produces events.
4. Where the traps / failure modes are: **httpx refuses non-ASCII header values entirely** (`UnicodeEncodeError` client-side), so the non-ASCII secret test drives a raw ASGI call with `\xe9` bytes — same technique as C22's raw-ASGI probe; `request.json()` can raise on malformed bodies — wrapped into a 400; `config` is read-modify-written as a whole (JSONB) so `last_update_id` updates atomically with the event commit; the exact-replay path is normally caught by the older-than-last guard BEFORE the idempotency insert, so the `created=False` branch is defense-in-depth for races.
5. How to verify it: `docker compose up -d postgres`, `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:5432/integro`, from `backend/`: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (50 files), `pytest` -> **231 passed** on a freshly recreated database (220 previous + 11 telegram tests: happy text message with full payload + enqueue + `last_update_id`, wrong/missing secret 401, non-ASCII secret 401 via raw ASGI, unknown 404, inactive 404, exact replay ignored with one row, older update_id ignored without event, photo ignored with captured log and no row, bare callback_query ignored with log, enqueue count stays 1 through mixed traffic). Mutation self-checks (both required): older-than-last comparison removed -> the old-update test FAILS; non-text guard removed -> the photo test FAILS; restored -> suite green.
