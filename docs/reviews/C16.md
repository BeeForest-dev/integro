# C16 — api.rbac

## Contract
```
Purpose:    role-based access dependency for routes.
In -> Out:  allowed request or 403.
Errors:     missing membership -> 403 (not 404, to avoid existence probing);
            insufficient role -> 403 with the required role in the detail.
Side fx:    none.
Deps:       fastapi, services.auth.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/api/security.py` provides three FastAPI dependencies: `get_current_claims(request, settings)` — bearer extraction + `verify_access_token`, any token problem -> 401 "Invalid credentials" (generic, byte-identical to C15); `get_current_membership(request, claims, session)` — resolves the membership through `OrgScope` (C12) with the token's org, missing membership -> 403 "no membership in this organization" (never 404, so responses cannot probe organization existence); `require_roles(*allowed: MembershipRole)` — a dependency factory rejecting any role outside the explicit set with 403 and the required roles in the detail ("requires one of: owner, admin").
2. Why it is built this way: the role always comes from the membership row in the database, never from the token — a stolen or forged token cannot grant privileges the DB does not confirm; the allowed-role set is the explicit call-site argument with no hierarchy and no prebuilt constants, so every route states exactly who may pass and the 403 detail names that set; membership is a chained dependency (claims -> membership -> role guard), so every guard reuses one verified path instead of re-implementing token parsing.
3. How it is structured internally: pure dependency functions over FastAPI's `Depends` — `get_settings` (per-request `Settings`), `get_current_claims`, `get_current_membership`, `require_roles(*allowed)` returning an inner async guard; only `uuid`, `fastapi`, `app.core`, `app.db.engine.get_session`, `app.models`, `app.repositories.org_scope`, `app.services.auth.tokens` are touched — C15 is not modified.
4. Where the traps / failure modes are: 401-vs-403 boundaries matter — token problems are 401 (unauthenticated), membership/role problems are 403 (authenticated but not allowed); the deleted-membership case must stay 403 with the shared message, never 404, or the endpoint becomes an org-existence oracle; `require_roles` must not fall for a "role hierarchy" shortcut — the check is plain set membership; the scratch-app tests register the C03 handlers, otherwise AppError would surface as an unhandled 500; tests keep the C15 engine-per-request discipline (asyncpg connections are loop-bound).
5. How to verify it: `docker compose up -d postgres`, `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:5432/integro`, from `backend/`: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (35 files), `pytest` -> **109 passed** (103 previous + 6 new: owner passes, viewer gets 403 naming owner/admin, deleted membership -> 403 with the shared message, no bearer -> 401, expired -> 401, refresh-as-access -> 401). Mutation self-checks (both required): role check removed -> viewer test FAILS; membership-None branch removed -> deleted-membership test FAILS; restored -> suite green.
