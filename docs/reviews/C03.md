# C03 — core.errors

## Contract
```
Purpose:    unified exception -> RFC 7807 problem-details response.
In -> Out:  JSON {type,title,status,detail,instance,errors[]}.
Errors:     domain error -> mapped status; unknown error -> 500 with generic text,
            internal detail only in logs, never in the response body.
Side fx:    none.
Deps:       fastapi.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/core/errors.py` provides `AppError` — a base domain exception carrying `status_code`, `title`, `detail`, `errors[]` and an RFC 7807 `type` — plus three async handlers and `register_error_handlers(app)`. Every failure becomes one JSON body `{type, title, status, detail, instance, errors[]}` with media type `application/problem+json`; `instance` is the request path.
2. Why it is built this way: the contract needs one unified mapping, so there is a single private `_problem_response` builder that all three handlers share — the body shape exists in exactly one place. `AppError` takes its status/title from class attributes (defaults 500/"Internal Server Error") so later contracts (C12 `ScopeError`, C14 `TokenExpired`/`TokenInvalid`) can subclass with one line. A catch-all `Exception` handler guarantees the "unknown error -> 500" case even for bugs nobody anticipated.
3. How it is structured internally: `AppError` (constructor + `_type_slug` deriving `urn:integro:error:<snake_case_class_name>`) -> `_problem_response` (builds the dict + JSONResponse) -> three thin handlers: `app_error_handler` (domain error -> declared status), `validation_error_handler` (FastAPI `RequestValidationError` -> 422, `errors[]` filled with `{loc, msg}` per field), `unhandled_error_handler` (logs via stdlib `logging` with traceback, returns generic 500) -> `register_error_handlers` wires all three onto the app. No module-level side effects; no DB, no env, no config reads.
4. Where the traps / failure modes are: the unknown-error handler must never leak internals — the test asserts the secret string appears in `caplog` but NOT in the response body; the two `type: ignore[arg-type]` lines in registration are required because starlette's registry is typed for the broad `Exception` base while the handlers narrow it (safe at runtime — each handler is registered only for its own class); starlette in this env deprecates `HTTP_422_UNPROCESSABLE_ENTITY`, so the literal `422` is used; `JSONResponse` renders without spaces after colons, so tests assert on parsed JSON, not substrings.
5. How to verify it: `cd backend && .venv\Scripts\python.exe -m pytest tests -v` — 17 tests pass (7 C01 + 4 C02 + 6 C03: domain status mapping, full six-key body, `errors[]` passthrough, detail-defaults-to-title, unknown error -> generic 500 with internal detail only in logs, 422 validation mapping, handler registration). `ruff check .` and `mypy app` both clean.
