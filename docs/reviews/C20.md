# C20 — models.flow (+ flow_versions)

## Contract
```
Purpose:    flow row + versioned JSON definition + enabled flag.
In -> Out:  persisted flow; definition validated against the JSON schema before write.
Errors:     definition fails schema -> 422 with the exact path that failed;
            unknown trigger/action type -> 422 listing supported types.
Side fx:    tables `flows`, `flow_versions`.
Deps:       models, schemas.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `app/models/flow.py` defines `Flow` (id, organization_id FK, name, enabled default True, created_at) and `FlowVersion` (id, flow_id FK, version int, definition JSONB, created_at) with `unique(flow_id, version)`; migration `0009_flows` creates both tables; deliberately NO current_version FK on Flow — "latest" is always `max(version)`. `app/schemas/flow_definition.py` provides the pydantic v2 `FlowDefinition(trigger, actions)` where `Trigger.type` and `Action.type` are validated by a field validator against `SUPPORTED_TYPES` from `app.models` (C18 — the single registry), the error naming the supported list. `app/repositories/flows.py` (OrgScope-first): `create_flow` (validates BEFORE any insert, writes flow + version 1 in one transaction), `update_flow_definition` (max+1; foreign flow -> None), `set_enabled`, `get_flow`/`list_flows` via OrgScope, `version_history` (asc), `get_current_definition` (max version). Validation failures raise `AppError` 422 with detail `"<json-path>: <message>"` for the first failure.
2. Why it is built this way: validating in the repository before insert means a bad definition never produces a database error or a half-written flow; the registry lives in exactly one place (`SUPPORTED_TYPES`), so trigger/action/connector types cannot drift apart; version history is append-only with a database-level uniqueness guarantee — no optimistic-locking machinery needed; "latest = max(version)" avoids a circular FK between flows and flow_versions.
3. How it is structured internally: schema layer (`app/schemas/flow_definition.py`, pydantic) is separate from the repository, which converts `ValidationError` into the 422 problem-details shape (`trigger.type: unsupported type '...'`); `FlowVersion` has no organization_id, so version reads prove ownership via `scope.get(Flow, ...)` first and then query by `flow_id` on the raw session — the documented trust-boundary pattern (same as the auth lookup); every other read goes through OrgScope.
4. Where the traps / failure modes are: pydantic v2 loc paths for nested lists look like `actions.0.type` — the tests pin the exact format; the first-failure-wins detail must include the supported list for type errors; `update_flow_definition` must resolve the flow through the scope BEFORE appending a version, or a foreign flow_id would accept a version row (caught in review of my own draft); mutation procedure lesson from C11 applied: schema mutations are proven by rebuilding from `downgrade base`, not `downgrade -1`.
5. How to verify it: `docker compose up -d postgres`, `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:5432/integro`, from `backend/`: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (42 files), `pytest` -> **140 passed** on a freshly recreated database (131 previous + 9 flow tests: migration cycle, create + v1, monotonic/unique versions, missing trigger -> 422 path, unknown trigger type -> 422 with list, unknown action type -> 422 path, enabled toggle, tenant isolation, history order). Mutation self-checks (both required): validation bypassed in create -> bad-type test FAILS; unique(flow_id, version) removed from the migration (fresh schema rebuild) -> double-version test FAILS; restored -> suite green.
