# C01 — core.config

## Contract
```
Purpose:    load and validate application settings from environment.
In -> Out:  Settings object (immutable) from env + .env file.
Errors:     missing required var -> app refuses to start with a named error;
            invalid type (e.g. DATABASE_URL="foo") -> validation error naming the field.
Side fx:    reads env / .env only.
Deps:       pydantic-settings.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: Loads and validates the application settings (`DATABASE_URL`, `REDIS_URL`, `SECRET_KEY`) from process environment variables and an optional `.env` file, and exposes them as an immutable `Settings` object.
2. Why it is built this way: `pydantic-settings` `BaseSettings` gives env + `.env` file loading, per-field validation and named `ValidationError`s out of the box — so a missing/invalid variable makes the app refuse to start with an error that names the field, exactly as the contract requires. `PostgresDsn` turns `DATABASE_URL="foo"` into a validation error naming `DATABASE_URL`.
3. How it is structured internally: A single `Settings` class in `backend/app/core/config.py` with `SettingsConfigDict(env_file=".env", extra="ignore", frozen=True)`; no module-level instance, no side effects beyond reading env/`.env`.
4. Where the traps / failure modes are: Tests must scrub the real environment (`autouse` fixture) so leaked vars cannot mask a missing-var failure; `.env` file lookup is relative to the CWD, so tests pass `_env_file` explicitly; `frozen=True` means mutation raises `ValidationError`, not `AttributeError`.
5. How to verify it: `cd backend && python -m pytest tests -v` — 7 tests, one per contract error case (missing var per field ×3, invalid `DATABASE_URL`, plus happy paths for env/`.env` loading and immutability).
