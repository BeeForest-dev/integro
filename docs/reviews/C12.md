# C12 — repositories.org_scope

## Contract
```
Purpose:    single choke point that adds `organization_id` to every query.
In -> Out:  repository methods that never accept an org id from the caller.
Errors:     query without org scope -> raises `ScopeError` (never returns cross-tenant rows).
Side fx:    none beyond reads.
Deps:       sqlalchemy.
```
> This module is the anti-leak mechanism. It gets the most review attention.

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/repositories/org_scope.py` provides `OrgScope` — a per-request object holding one session and one organization id (established from the authenticated membership; C16 will own that construction). All reads funnel through it: `query(model)` builds a pre-scoped SELECT, `get(model, row_id)` fetches by primary key inside the scope, `all`/`first`/`execute` run statements after proving scope. `ScopeError` (C03 `AppError`, generic 500) is raised before anything unscoped touches the database.
2. Why it is built this way: the choke point *validates* rather than silently rewrites statements — a developer sees `ScopeError` immediately instead of wondering why their WHERE clause was ignored; equality is the only accepted shape (a pinned `organization_id = <this org>`, either operand order) because exotic filters (`IN`, OR-branches) cannot be proven safe, and rejecting them visibly is the safe default for an anti-leak mechanism; cross-tenant primary-key lookups return `None` (indistinguishable from missing), never the row.
3. How it is structured internally: `_pins_organization_id()` walks the WHERE clause (`visitors.iterate`) for a `BinaryExpression` with `operators.eq` on an `organization_id` column whose bound value equals the scope's org; `OrgScope` methods (`query`, `get`, `all`, `first`, `execute`, `_org_column`) are thin and total ~150 lines; models without `organization_id` (`User`, `Organization` itself) are rejected because they cannot be scoped. ScopeError surfaces through the C03 handlers as a generic 500 with no internals.
4. Where the traps / failure modes are: the enforced invariant is equality-only and single-entity — `IN`-scoped, `OR`-branched, `UNION`-ed, raw-`text()`, and multi-entity statements are all rejected loudly (documented trade-off: false rejections are visible and fixable by splitting the query, false acceptances would be silent leaks; an `or_(org == A, org == B)` in particular would launder a cross-tenant read through the scope's own pin); the scope guards statements routed through it — raw `session.execute` outside the scope remains a code-review responsibility, which is why C18+ repositories must accept `OrgScope` and never a session; relationship lazy-loading issues PK-lookups, not list scans, so it cannot enumerate another tenant's rows; constructing `OrgScope` with a caller-supplied org id is the documented trust boundary until C16 verifies the membership. Mutation self-checks (both rounds): disabling the pin validation, the OR rejection, or the single-FROM requirement each makes the corresponding adversarial test FAIL — the backup is always taken and verified in a separate step before mutating (a backup taken in the same parallel step as the mutation once captured the mutated file and cost a restore cycle).
5. How to verify it: `docker compose up -d postgres`, `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:5432/integro`, from `backend/`: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (23 files), `pytest` -> **69 passed** (65 previous + 4 adversarial: OR-poisoned query rejected with no foreign id obtainable, `union()` rejected, `text()` rejected, two-entity select rejected; on top of the original 8: scoped query returns only own rows, `get` hides cross-tenant ids, unscoped SELECT rejected, foreign-org SELECT rejected, correctly scoped statement passes, models without org column rejected, ScopeError shape is a generic 500, scope requires an organization). All 12 run against real PostgreSQL with two seeded organizations — no skips (unset DATABASE_URL fails loudly).

## Verdict (written by the reviewer)
**Result:** CHANGES_REQUESTED

| Gate | Result | Comment |
|---|---|---|
| G1 Conformance | fail | The architecture is right — one `execute` choke point, pre-scoped `query()`, cross-tenant `get()` returning None, `ScopeError` as a 500 AppError. But the module's own guarantee ("an unscoped query can never return cross-tenant rows because it never runs") is falsifiable today. Reviewer-run adversarial probes against a real PG16: (1) `or_(org == A, org == B)` is ACCEPTED and returns B's row — a real cross-tenant leak through the choke point, because the inspector stops at the first matching equality pin; (2) a `union()` statement raises `AttributeError: 'CompoundSelect' object has no attribute 'whereclause'` instead of `ScopeError`; (3) `text(...)` likewise raises `AttributeError`. The contract's error semantics ("query without org scope -> raises ScopeError") are violated for anything that is not a plain Select. |
| G2 Tests | pass | 65 passed on real PG16 (8 new tests), ruff/mypy clean (23 files), no skips. The honest-path tests are exactly the right ones, and the reviewer's mutation (pin check bypassed) makes `test_unscoped_query_is_rejected` and `test_foreign_scope_query_is_rejected` FAIL as required. | G3 Boundaries | pass | ScopeError carries no internals; cross-tenant id is indistinguishable from missing; no I/O beyond the guarded session; no new dependencies. |

### Required changes
1. **Reject `or_` anywhere in the WHERE clause** (traverse the whole tree; any `BooleanClauseList` with the `or` operator -> ScopeError). This is consistent with the module's own stated philosophy — false rejections of exotic-but-honest queries are visible and fixable, false acceptances are silent and fatal. Honest OR use-cases get two scoped queries instead.
2. **Reject non-Select statements with ScopeError**: `execute()` starts with `isinstance(statement, Select)` so `text()` and `CompoundSelect`/`union()` raise ScopeError instead of AttributeError.
3. **Require a single FROM entity**: the statement's final FROM list must be exactly one entity and the pinned `organization_id` column must belong to it (`select(Membership, User).where(Membership.organization_id == A)` must be rejected). Today this rejects nothing honest (the whole suite stays green); it future-proofs M2+ when more org-scoped tables appear and join-poisoning becomes possible (pin via the joined table, select an unscoped root).
4. Fix the module docstring to state the enforced invariant precisely (no unqualified "never").
5. Tests: OR-poison -> ScopeError (and assert no foreign row id can be obtained), union -> ScopeError, `text()` -> ScopeError, two-entity select -> ScopeError. Self-checks: with change 1 removed the OR test must fail; with change 3 removed the two-entity test must fail.
