# C15 — api.auth

## Contract
```
Purpose:    register, login, refresh, me.
In -> Out:  JSON with tokens and user profile; sets an httpOnly refresh cookie.
Errors:     wrong credentials -> 401 generic message (no "user exists" leak);
            duplicate email -> 409.
Side fx:    inserts user + membership; writes an audit record.
Deps:       services.auth, repositories.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/api/auth.py` exposes POST `/auth/register` (organization + owner user, one transaction, audit row, token pair, httpOnly refresh cookie), POST `/auth/login` (oldest membership, generic 401 for every credential failure), POST `/auth/refresh` (cookie-only rotation; a body token is never accepted), GET `/auth/me` (Bearer access token; role read from the membership through OrgScope with the token's org). New repositories `users.create_user` (409 on duplicate email, C10 pattern) and `memberships.create_membership`; minimal `services/audit.py` + `AuditLog` model + migration `0006_audit_log`; services `auth/registration.py` and `auth/login.py` orchestrate; the router stays thin and wires `Settings.SECRET_KEY` down explicitly.
2. Why it is built this way: registration composes three repository inserts inside one transaction — a duplicate email rolls back the organization insert too (the C10 rollback-on-IntegrityError pattern); "Invalid credentials" is a single shared AppError raised on both failure branches, so the 401 body is byte-identical and cannot probe account existence; the refresh token never appears in any request body — only the httpOnly `integro_refresh` cookie (path=/auth, samesite=lax, max_age=7 d, secure=False for the local demo); login and /me read global tables (users, memberships, organizations) directly — that IS the trust boundary that establishes the OrgScope, documented in the module.
3. How it is structured internally: router (`api/auth.py`: payload models, cookie helper, bearer parsing, serialization) -> services (`registration.register`, `login.login` — both return `AuthResult`) -> repositories (C10 patterns) -> models; `get_session` dependency from C04; settings injected per request via a `get_settings` dependency (no module-level env reads); audit recorded in-transaction via `services/audit.record_audit` (C19 owns failure isolation).
4. Where the traps / failure modes are: HS256 tokens are deterministic — a rotation within the same second yields identical tokens, so the rotation test sleeps across a second boundary; each in-process request runs in its own `asyncio.run`, so the test helper creates AND disposes the engine inside that loop (asyncpg connections are loop-bound); login's oldest-membership ordering uses `(created_at, id)` as tiebreak; the httpx deprecation warning for per-request `cookies=` is cosmetic (one test passes a forged cookie); the first mutation attempt for the 401-equality test used the same message on both branches and stayed green — a real leak message ("Unknown email") makes it fail as required.
5. How to verify it: `docker compose up -d postgres`, `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:5432/integro`, from `backend/`: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (34 files), `pytest` -> **102 passed** (90 previous + 12 auth scenarios). Mutation self-checks (all required, all verified): unknown-email message split -> identical-401 test FAILS; register audit record removed -> register happy-path test FAILS; cookie httpOnly removed -> register happy-path test FAILS; each restored from separately verified backups -> suite green.
