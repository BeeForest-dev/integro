# C21 — services.conditions

## Contract
```
Purpose:    evaluate a JSON condition tree against an event payload.
In -> Out:  boolean + list of failed clause paths (for the UI).
Errors:     unknown operator -> validation error at save time, never at runtime;
            missing field in payload -> condition evaluates False, not an exception.
Side fx:    none. NO `eval()` — explicit operator registry only.
Deps:       stdlib only.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/services/conditions.py` (stdlib only) evaluates condition trees — `{"all": [...]}` / `{"any": [...]}` nestable combinators with leaf clauses `{"field": "a.b.c", "op": name, "value": ...}` — against an event payload, returning `EvaluationResult(matched, failed_paths)` with UI-rendered entries like `"all[0]: amount gt 100"`. The operator registry (dict of predicates) covers `eq/ne/gt/gte/lt/lte` (numeric; type mismatch -> False), `contains` (substring or list membership) and `exists`. `validate_conditions(tree)` raises `ConditionValidationError(ValueError)` with the JSON path of the first problem. Save-time wiring (the one allowed C20 touch): `FlowDefinition` gains optional `conditions: dict | None` validated by a field validator delegating to `validate_conditions`, so bad conditions fail at flow save with the existing C20 422 machinery.
2. Why it is built this way: explicit operator registry instead of `eval` is the contract's core safety property — the module cannot execute attacker-shaped input by construction; evaluation never raises (unknown op, missing field, type mismatch, even a misbehaving predicate all degrade the clause to False with its path recorded), while save-time validation is strict and names the exact failing path; `all`/`any` children are evaluated EAGERLY so `failed_paths` is complete for the UI even when an early clause already decided the outcome.
3. How it is structured internally: `_OPERATORS` registry of small predicates; `_lookup` (dot-path with a `_MISSING` sentinel so `None` remains a legitimate value); `_validate_node`/`_validate_clause` (strict, first-problem-wins, root paths `all`/`any`/`$`); `_evaluate_node` (never-raising, renders failed paths); `evaluate`/`validate_conditions` as the public API; `EvaluationResult` frozen dataclass. The schema layer depends on the service; the service depends on nothing but stdlib.
4. Where the traps / failure modes are: Python's `all()` generator SHORT-CIRCUITS — using it directly would skip evaluating later clauses and silently drop their failed paths (caught by the failed-paths test); `bool` is an `int` subclass, so the numeric operators explicitly reject booleans; `contains` flips operand order deliberately (payload value is the container, configured value is the needle); pydantic wraps validator `ValueError`s into `Value error, ...` messages, so the 422 detail is asserted by substring, not exact equality; the `"eval(" absence` test reads the module source at test time — a comment containing that string would fail the suite.
5. How to verify it: no database needed for the evaluator: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (43 files), `pytest` -> **169 passed** on a freshly recreated database (140 previous + 29 condition/parametrized tests + 1 flow-integration test): numeric truth tables with exact boundaries, contains substring/list, exists, nested dot paths, missing field -> False + rendered path, all/any nesting with documented vacuous truth (empty all True, empty any False), complete failed-path rendering, save-time validation (unknown op with path + supported list, five malformed-tree shapes), runtime unknown op -> False without raise, `eval(`/`exec(` absent from the module source, and create-flow-with-bad-conditions -> 422 through the C20 repository. Mutation self-checks (both required): `gte` dropped from the registry -> its truth-table cases FAIL; missing-field turned into a raise -> the missing-field test FAILS; restored -> suite green.
