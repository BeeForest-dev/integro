# C11 — models.user + models.membership

## Contract
```
Purpose:    user row + membership linking a user to an org with a role.
In -> Out:  persisted rows; role in {owner, admin, member, viewer}.
Errors:     role not in the enum -> validation error.
Side fx:    tables `users`, `memberships`.
Deps:       sqlalchemy.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/models/user.py` defines `User(Base)` — id (`sa.Uuid`, primary key, `default=uuid4`), email (not null, unique, indexed), created_at (timezone-aware, `server_default=now()`). `backend/app/models/membership.py` defines `MembershipRole` (`StrEnum`: owner/admin/member/viewer, lowercase values) and `Membership(Base)` — id, user_id FK → `users.id`, organization_id FK → `organizations.id`, role, created_at. A `@validates("role")` validator coerces strings to the enum and raises `ValueError` for anything outside it. Migration `0003_users_memberships` creates/drops both tables.
2. Why it is built this way: role validation lives in the model (not the database check) so the error is a plain Python `ValueError` at assignment time — exactly the "validation error" the contract names, and directly mappable to a 422 at the API edge later; SQLAlchemy persists the enum VALUES (`owner`...) via `values_callable`, because by default it persists member NAMES (`OWNER`...) — caught during migration review; `native_enum=False` keeps the column a plain varchar (no PG enum type to manage on downgrade).
3. How it is structured internally: models in `app/models` (imported from `app/models/__init__.py` so `Base.metadata` sees them — `alembic/env.py` already imports `app.models`); FKs by string reference (no import cycles); migration generated with `alembic revision --autogenerate` against real PostgreSQL 16 from `docker compose up -d postgres` and verified: upgrade head creates both tables, downgrade base drops them, re-upgrade is clean (`current = 55f4a25579a2 (head)`).
4. Where the traps / failure modes are: the first autogenerate silently produced name-based enum values — `values_callable` fixed it and the regenerated migration was re-verified up/down/re-up; SQLAlchemy's SAEnum alone raises `LookupError` wrapped in `StatementError` on a bad role, which is not a validation error — hence the `@validates` coercion; as in C10, each test creates/uses/disposes its engine inside one coroutine (asyncpg connections are loop-bound), and without `DATABASE_URL` all 5 tests fail loudly — no skips (verified); generated migration lines over the 100-char lint limit are hand-wrapped.
5. How to verify it: `docker compose up -d postgres` (port 5432 published per the reviewer's C10 housekeeping), `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:5432/integro`, from `backend/`: `ruff check .` -> clean, `mypy app --warn-unused-ignores` -> clean (22 files), `pytest` -> **54 passed** (49 previous + 5 new: migration up/down/re-up, user+membership persist with role round-trip, all four contract roles persist, invalid role -> ValueError with a clear message, uuid pk + created_at defaults). The migration was also driven manually through the alembic CLI on the same database (exit 0 each way). CI: the C08 workflow provides the postgres service container, so the new tests run there unchanged.
