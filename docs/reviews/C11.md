# C11 — models.user + models.membership

## Contract
```
Purpose:    user row + membership linking a user to an org with a role.
In -> Out:  persisted rows; role in {owner, admin, member, viewer}.
Errors:     role not in the enum -> validation error.
Side fx:    tables `users`, `memberships`.
Deps:       sqlalchemy.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/models/user.py` defines `User(Base)` — id (`sa.Uuid`, primary key, `default=uuid4`), email (not null, unique, indexed), created_at (timezone-aware, `server_default=now()`). `backend/app/models/membership.py` defines `MembershipRole` (`StrEnum`: owner/admin/member/viewer, lowercase values) and `Membership(Base)` — id, user_id FK → `users.id`, organization_id FK → `organizations.id`, role, created_at. A `@validates("role")` validator coerces strings to the enum and raises `ValueError` for anything outside it. Migration `0003_users_memberships` creates/drops both tables.
2. Why it is built this way: role validation lives in the model (not the database check) so the error is a plain Python `ValueError` at assignment time — exactly the "validation error" the contract names, and directly mappable to a 422 at the API edge later; SQLAlchemy persists the enum VALUES (`owner`...) via `values_callable`, because by default it persists member NAMES (`OWNER`...) — caught during migration review; `native_enum=False` keeps the column a plain varchar (no PG enum type to manage on downgrade).
3. How it is structured internally: models in `app/models` (imported from `app/models/__init__.py` so `Base.metadata` sees them — `alembic/env.py` already imports `app.models`); FKs by string reference (no import cycles); migration generated with `alembic revision --autogenerate` against real PostgreSQL 16 from `docker compose up -d postgres` and verified: upgrade head creates both tables, downgrade base drops them, re-upgrade is clean (`current = 55f4a25579a2 (head)`).
4. Where the traps / failure modes are: the first autogenerate silently produced name-based enum values — `values_callable` fixed it and the regenerated migration was re-verified up/down/re-up; SQLAlchemy's SAEnum alone raises `LookupError` wrapped in `StatementError` on a bad role, which is not a validation error — hence the `@validates` coercion; as in C10, each test creates/uses/disposes its engine inside one coroutine (asyncpg connections are loop-bound), and without `DATABASE_URL` all 5 tests fail loudly — no skips (verified); generated migration lines over the 100-char lint limit are hand-wrapped.
5. How to verify it: `docker compose up -d postgres` (port 5432 published per the reviewer's C10 housekeeping), `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:5432/integro`, from `backend/`: `ruff check .` -> clean, `mypy app --warn-unused-ignores` -> clean (22 files), `pytest` -> **57 passed** (54 previous + 3 new integrity tests). The migration was also driven manually through the alembic CLI on the same database (upgrade/downgrade/re-upgrade exit 0, `current = ac7e068c9197 (head)`).

### Fixes applied (implementer, 2026-11-06) — the CHANGES_REQUESTED round
1. `backend/alembic/versions/0004_membership_integrity.py` — new migration (0003 untouched, as pushed): composite unique `uq_memberships_user_organization` on `memberships(user_id, organization_id)` and CHECK `ck_memberships_role` (`role IN ('owner','admin','member','viewer')`), both dropped in downgrade. Written with `op.batch_alter_table` so the migration still runs on the SQLite scratch databases of the C05 fast tests — plain `create_unique_constraint` broke them with `NotImplementedError: No support for ALTER of constraints in SQLite dialect` (caught by the full suite).
2. `backend/app/models/membership.py` — `__table_args__` mirrors both constraints (`UniqueConstraint`, explicit `CheckConstraint`); `SAEnum` gained `create_constraint=False` so metadata carries exactly the one CHECK and future autogenerates stay in sync.
3. `backend/tests/models/test_users_memberships.py` — three new tests: duplicate (user_id, organization_id) pair -> `IntegrityError`; raw stored role is lowercase — a raw SQL `INSERT ... 'ADMIN'` must be rejected by the database and a proper value reads back `"admin"` via `text("SELECT role FROM memberships")` (this is what makes the CHECK-mutation detectable; a plain round-trip test alone could not); reflection proves the composite unique and the role CHECK exist.
4. Mutation self-checks (both re-run against the final batch-mode migration):
   - CHECK removed from the migration -> `test_raw_stored_role_is_lowercase` FAILS (`1 failed`); pg_constraint listing confirms `ck_memberships_role` absent.
   - Unique removed from the migration, fresh schema rebuilt from `downgrade base` -> `test_duplicate_membership_pair_raises_integrity_error` FAILS together with the reflection test; pg_constraint listing confirms `uq_memberships_user_organization` absent. (Lesson recorded: mutating a migration and re-applying with `downgrade -1` can leave the old constraint in place — the mutated downgrade never drops it; only a base-to-head rebuild proves the mutation.)

### Required changes
1. New migration `0004_membership_integrity` (never edit pushed 0003): add the composite unique constraint on `memberships(user_id, organization_id)` and a CHECK constraint on `role IN ('owner','admin','member','viewer')`. Mirror both in the model (`UniqueConstraint` in `__table_args__`; `SAEnum(..., create_constraint=True)` or an explicit `CheckConstraint`) so future autogenerates stay in sync.
2. Tests: (a) inserting a second membership for the same (user, organization) pair raises `IntegrityError`; (b) reflection shows the composite unique constraint; (c) the raw stored role is lowercase — read it back with `text("SELECT role FROM memberships")` and assert `"admin"`, not the enum round-trip.
3. Self-checks before delivery: with the CHECK removed, test (c) must fail; with the unique constraint removed, test (a) must fail.
