# C13 — services.auth.password

## Contract
```
Purpose:    hash and verify passwords.
In -> Out:  argon2 hash string / boolean.
Errors:     invalid hash -> False, no exception; empty password -> validation error.
Side fx:    none.
Deps:       argon2-cffi.
```

Standing requirement recorded by the C11 reviewer: C13 adds the
`users.password_hash` column via its own migration so C14/C15 can use it.

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/services/auth/password.py` provides `hash_password(password) -> str` (argon2id with a random salt per call) and `verify_password(password_hash, password) -> bool`. It also delivers the standing requirement: `users.password_hash` (nullable `String`) on the `User` model plus migration `0005_user_password_hash` adding/dropping the column.
2. Why it is built this way: argon2-cffi's `PasswordHasher` with default parameters is the allow-listed, battle-tested implementation; a malformed stored hash returns `False` instead of raising, so a corrupted `password_hash` row degrades to "login fails" rather than a 500; empty-password validation is a plain `ValueError` (the contract's "validation error"), raised before any hashing so both functions share one rule.
3. How it is structured internally: one module-level `PasswordHasher`, a private `_require_password` guard, and the two public functions; no state, no I/O. `verify_password` catches `(VerificationError, InvalidHash)` — in argon2-cffi 25.1.0 `InvalidHash` is NOT a subclass of `VerificationError` (verified empirically with `issubclass`), so both are named explicitly; missing `InvalidHash` makes the malformed-hash tests fail (mutation-proven).
4. Where the traps / failure modes are: the exception hierarchy changed across argon2-cffi versions — catching only `VerificationError` silently lets `InvalidHash` escape, which is exactly why the parametrized malformed-hash test exists and why the mutation removes `InvalidHash`; the column is nullable so the 69 pre-existing tests that create users without passwords stay untouched; migration is a plain `add_column`/`drop_column` (SQLite-compatible, so the C05 scratch tests keep passing).
5. How to verify it: `docker compose up -d postgres`, `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:5432/integro`, from `backend/`: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (26 files), `pytest` -> **78 passed** (69 previous + 9 new: argon2id hash verifies, random salt, wrong password -> False, malformed hash -> False x3 parametrized, empty password -> ValueError on hash and verify, real-PG roundtrip of the new column). Migration verified on real PG16 via CLI: `upgrade head` -> `current: 47461697779b (head)`, `downgrade base`, re-`upgrade head` — all exit 0. Mutation self-check: `InvalidHash` removed from the except clause -> all malformed-hash tests FAIL; restored -> 78 passed.
