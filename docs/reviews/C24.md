# C24 — connectors.triggers.cron

## Contract
```
Purpose:    scheduled trigger firing a flow on an interval or cron expression.
In -> Out:  event payload with the schedule and the previous run timestamp.
Errors:     invalid cron -> validation error when the flow is saved;
            missed schedule (worker down) -> one catch-up run, not N.
Side fx:    uses celery beat.
Deps:       celery.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `SUPPORTED_TYPES` gains `"schedule"` and the `Trigger.config` for it must be exactly `{"every_seconds": int > 0}` or `{"cron": "5-field string"}` — validated at save time in `app/schemas/flow_definition.py` (invalid cron / both keys / zero interval -> 422 through the existing C20 machinery). `app/services/cron.py` (stdlib only) parses five-field cron (minute hour dom month dow; `*`, `*/n`, `a`, `a-b`, `a-b/n`, comma lists; dow 7 = Sunday) and finds the next slot; bad syntax raises `CronError(ValueError)` naming the field. `Flow` gains `next_run_at` (migration `0011_flow_schedule`). `app/workers/scheduler.py` provides `tick_schedules` (beat entry in `celery_app.conf`, every 60 s): for each enabled flow with a schedule trigger whose `next_run_at` is due (or NULL = never initialized, slot = `created_at`), it advances `next_run_at` FIRST (interval: now + every_seconds; cron: next slot strictly after now), then stores the event idempotently as `schedule:{flow_id}:{slot_iso}` with payload `{"schedule": config, "previous_run_at": iso|null, "scheduled_at": slot_iso}` and enqueues `process_event` — exactly once, even under double ticks.
2. Why it is built this way: exactly-once comes from the C22 unique index with the slot in the key — no locking; advancing before storing means a crash between the two loses the slot (documented, "move on") instead of double-firing it; catch-up fires ONCE for the latest missed slot and moves on — never a loop; the beat is ONE static periodic task (not per-flow schedules), so adding flows never touches beat configuration; the cron semantic is AND for dom/dow (documented simplification vs classic cron's OR rule — flagged for the owner).
3. How it is structured internally: parser (`parse_cron`/`next_slot`/`CronError`) in `services/cron.py`; save-time config validation in the C20 schema file (the allowed touch); the tick is a `shared_task` around an async core (`_tick_schedules`) so tests drive the coroutine directly without a beat or broker; the enqueue seam (`_enqueue_process_event`) is lazy-imported like C22; `celery_app.py` gains the scheduler module in `include` plus the `tick-schedules` beat entry (the second allowed C07 touch, one file edit).
4. Where the traps / failure modes are: **the double-tick test as originally specified cannot detect a missing slot in the idempotency key** — for the SAME slot the key collides with or without it; the slot matters for DIFFERENT slots of the same flow (without it a flow would fire exactly once, ever), so the mutation-sensitive test re-arms `next_run_at` and asserts two successive slots produce two distinct-keyed events (the plain double-tick test stays as a sanity check) — reviewer mapping refined accordingly; `next_slot` iterates minute-by-minute with a 4-year cap (February-31st-style expressions raise `CronError`); dow uses `(weekday()+1) % 7` (Mon=0..Sun=6 -> Sun=0..Sat=6); the tick treats NULL `next_run_at` as due with `created_at` as the slot anchor, so a freshly created schedule flow fires on the first tick (catch-up semantics for its creation slot).
5. How to verify it: `docker compose up -d postgres`, `DATABASE_URL=postgresql+asyncpg://integro:integro@127.0.0.1:5432/integro`, from `backend/`: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (49 files), `pytest` -> **220 passed** on a freshly recreated database (182 previous + 38 new: parser field-form table, invalid syntax naming the field, next-slot minute/hour/day/month boundaries, strict-after, naive rejection, schema 422s, due-interval firing with payload assertions, not-ue untouched, disabled skipped, catch-up exactly-one with future next run, double tick one event, successive slots two events, cron flow landing on the next daily slot, NULL next_run_at initialization, beat entry in conf). Mutation self-checks (both required): catch-up replaced with a missed-slots loop -> the one-catch-up test FAILS; slot dropped from the idempotency key -> the successive-slots test FAILS; restored -> suite green.
