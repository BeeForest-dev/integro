# C14 — services.auth.tokens

## Contract
```
Purpose:    issue and verify access + refresh JWTs.
In -> Out:  signed token pair / decoded claims.
Errors:     expired -> typed `TokenExpired`; bad signature -> `TokenInvalid`;
            wrong audience/issuer -> `TokenInvalid`.
Side fx:    none. Secret from env.
Deps:       fastapi (jwt), core.config.
```

**Contract deviation (agreed with the reviewer, recorded in LOOP.md):** the
implementation is pure HS256 with `cryptography` (on the allow-list) instead
of PyJWT (not allow-listed), and takes the secret as an explicit parameter
instead of importing `core.config` — C15 wires `Settings.SECRET_KEY` at the
API edge.

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/services/auth/tokens.py` issues and verifies compact HS256 JWTs. `issue_token_pair(user_id, organization_id, secret, now=None) -> TokenPair(access_token, refresh_token)` with TTLs 900 s / 7 days (module constants); `verify_access_token(token, secret, now=None) -> dict` and `verify_refresh_token(...)` return the claims. Typed errors `TokenError` (base), `TokenExpired`, `TokenInvalid` live in the same module; C15 maps them to 401 at the API edge.
2. Why it is built this way: the header `{"alg":"HS256","typ":"JWT"}` is a fixed byte string, so there is no algorithm negotiation and `alg=none` is impossible by construction; signing is cryptography hazmat HMAC-SHA256, comparison is stdlib `hmac.compare_digest` (constant time); the secret is an explicit parameter, keeping the module pure, side-effect free, and independent of `Settings` (C15 does the wiring — the contract's own "Side fx: none" is preserved).
3. How it is structured internally: fixed-header constant; `_b64url_encode/decode` (padding-stripped), `_signature`, `_encode_token(claims, secret)` (also used by tests to craft adversarial tokens); `_verify(token, secret, expected_type, now)` is the single verification core used by both public verifiers. Claims: `iss="integro"`, `aud="integro-api"`, `sub`/`org` as strings, `typ` access|refresh, `iat`, `exp` (required). No role claim — roles come from the DB membership.
4. Where the traps / failure modes are: verification order matters — structure (exactly 3 parts) → header byte-identity → signature → iss/aud exact match → typ → exp presence → expiry → sub/org shape; `exp` must be a real number (`bool` is an `int` subclass in Python and is rejected); the alg=none test carries a signature that is VALID FOR THE FOREIGN HEADER — a forged-signature variant passes regardless of the header check (signature catches it anyway), so it could not detect a missing header check (first mutation round stayed green); the strengthened test makes the header check load-bearing and the mutation then fails as required.
5. How to verify it: no database needed for the token tests: `ruff check .` clean, `mypy app --warn-unused-ignores` clean (27 files), `pytest` -> **90 passed** (78 previous + 12 token tests: roundtrip claims, access/refresh cross-rejection, tampered payload, tampered signature, wrong secret, expired -> TokenExpired, missing exp -> TokenInvalid, wrong aud/iss -> TokenInvalid, alg=none with valid-for-that-header signature -> TokenInvalid, garbage string -> TokenInvalid, non-ASCII segments -> TokenInvalid, unicode injected into the payload segment -> TokenInvalid). Full suite (incl. PG-backed) run against compose postgres — green. Mutation self-checks: fixed-header check removed -> `test_alg_none_token_is_rejected` FAILS; ASCII guard removed -> both unicode tests FAIL; restored -> 90 passed.

## Verdict (written by the reviewer)
**Result:** CHANGES_REQUESTED

| Gate | Result | Comment |
|---|---|---|
| G1 Conformance | fail | The core is right and stays: fixed header byte-for-byte (alg=none impossible), signature checked with hmac.compare_digest BEFORE the payload is parsed, exp required with bool rejected, iss/aud/typ exact match, no role claim, secret as an explicit parameter. One defect: a token containing non-ASCII characters escapes as `UnicodeEncodeError` instead of the typed `TokenInvalid` - the reviewer verified it with a live probe (`verify_access_token("héllo.wörld.x", ...)` -> UnicodeEncodeError). Two places are exposed: the strict-ASCII header encode, and `urlsafe_b64decode` of the payload segment. An auth endpoint WILL receive arbitrary garbage; a 500 stack trace instead of a typed 401-path error violates the module's own "garbage -> TokenInvalid" promise. |
| G2 Tests | pass | 88 passed, ruff clean, mypy clean (27 files). Reviewer probes: alg=none, exp-as-string, exp-as-bool, payload-array, two-parts, empty string and expired all produce the correct typed errors. Mutations: removing the typ check makes `test_access_refresh_cross_rejection` FAIL; removing the exp check makes `test_expired_token_raises_token_expired` FAIL. |
| G3 Boundaries | pass | Constant-time signature comparison; authentication before parsing; no I/O; secret never logged; `cryptography` pinned in requirements.txt (allow-listed); no role in the token. |
| G4 Architecture | pass | Pure module, explicit secret parameter (C15 wires Settings.SECRET_KEY), internal `_encode_token` reused by tests, typed errors live beside the service. |
