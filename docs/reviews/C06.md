# C06 — api.health

## Contract
```
Purpose:    liveness/readiness/metrics endpoints for containers and monitoring.
In -> Out:  GET /health  -> 200 {"status":"ok"} (liveness, no deps)
            GET /ready   -> 200 {"db":true,"redis":true} / 503 (checks deps)
            GET /metrics -> Prometheus text format
Errors:     dependency down -> /ready returns 503 with the failing dependency name.
Side fx:    reads DB + Redis.
Deps:       fastapi, prometheus_client, redis.
```

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/api/health.py` exposes `GET /health` (pure liveness, zero I/O), `GET /ready` (DB + Redis probed in parallel, each under a 2 s timeout; 200 when all pass, 503 with a sorted `failed` list naming the dead dependencies) and `GET /metrics` (Prometheus text exposition of the default registry). `backend/app/main.py` adds `create_app()` with the C03 error handlers, the health router, and a lifespan that reads `Settings()` and initialises/disposes the engine (C04) and the Redis client; `app = create_app()` serves `uvicorn app.main:app`.
2. Why it is built this way: `check_database()` reuses the C04 probe instead of duplicating connection logic inside the router (layering: api -> db, no business logic in routers); the Redis client is a module-level singleton in `app/db/redis.py` (mirrors `engine.py`), so `/ready` costs exactly one `PING` per dependency per call; `Settings()` is read only inside the lifespan, so importing `app.main` and running lint/tests never needs environment variables.
3. How it is structured internally: `engine.py` gained only `check_database()` (probe -> `DatabaseUnavailableError`, `RuntimeError` before `init_engine`); `redis.py` has `init_redis(url)` / `dispose_redis()` / `check_redis()` (`redis.asyncio.Redis.from_url(..., decode_responses=True)`, `PING`); `health.py` keeps the check registry (`_DEPENDENCY_CHECKS`), the `READY_PROBE_TIMEOUT_SECONDS = 2.0` constant and three endpoints; no custom metrics are registered.
4. Where the traps / failure modes are: `httpx.ASGITransport` does not run the lifespan, so tests initialise the engine/Redis manually in a fixture — never relying on lifespan; the timeout is applied per probe via `asyncio.timeout(2.0)`, and a cancelled slow probe is converted to `False` (test asserts 503 arrives in < 3 s, not after the 60 s hang); `/ready` swallows every exception type (`except Exception` with an explicit `noqa: BLE001` — readiness must never 500); logs contain only the dependency name, never the DSN; `failed` is emitted only on 503 so the 200 body matches the contract exactly; mypy without the pydantic plugin sees env-backed `Settings` fields as required ctor args — one local `type: ignore[call-arg]` in `main.py` documents this instead of touching the pinned pyproject.
5. How to verify it: clean venv installed only from `backend/requirements.txt` (now + `uvicorn[standard]==0.54.0`, `redis==8.1.0`, `prometheus-client==0.26.0`): `ruff check .` -> All checks passed!, `mypy app` -> no issues in 12 files, `pytest -q` -> 36 passed (28 previous + 8 new: health without deps, ready 200, db-down 503, redis-down 503, both-down 503 sorted, slow-check timeout < 3 s, metrics exposition, real refused-DB 503). Live stand (docker pg16 + redis7, uvicorn): `/health` 200 `{"status":"ok"}`, `/ready` 200 `{"db":true,"redis":true}`, `/metrics` starts with `# HELP`/`# TYPE`; after `docker stop` of redis: `/ready` 503 `{"db":true,"redis":false,"failed":["redis"]}` while `/health` stays 200.

## Verdict (written by the reviewer)
**Result:** CHANGES_REQUESTED

| Gate | Result | Comment |
|---|---|---|
| G1 Conformance | pass | `/health`, `/ready`, `/metrics` behave exactly as specified, no extra endpoints or custom metrics. `app/main.py` and `check_database()` are within the authorised scope. 200 body is exactly `{"db":true,"redis":true}`; 503 carries a sorted `failed` list. |
| G2 Tests | fail | The contract's error case is covered for the DB path twice (stubbed and real refused connection), but the Redis path is only covered by a stub: `check_redis()` and `init_redis()` are never executed by the suite. A typo in `app/db/redis.py` (e.g. `_client.ping` instead of `_client.ping()`) would pass CI and fail in production. The live stand proves the path works today; it does not protect it. One test is missing — see Required changes. |
| G3 Boundaries | pass | Per-probe `asyncio.timeout(2.0)`, probes run in parallel, every failure maps to `false`, `/health` has zero I/O, no DSN/credentials in logs (checked the running process output for `postgres:test`, host:port and `password` — clean), `/metrics` exposes only the default registry. |
| G4 Architecture | pass | Downward imports (`api -> db`, `db -> core`), no business logic in the router, `Settings()` read only inside the lifespan so importing `app.main` needs no environment. Direct `api -> db` for infrastructure probes is acceptable; business endpoints must still go through `services`. |

### Non-blocking notes
1. `health.py` logs through stdlib `logging`, while C02 configures structlog. Nothing calls `setup_logging()` yet, so the whole app is currently on uvicorn's default format. Decide in C09 (`api.request_context`) that startup calls `setup_logging()` and modules use `structlog.get_logger()` with structured fields (`dependency=name`), not `%s`.
2. `type: ignore[call-arg]` is used and necessary; the proper fix is enabling the pydantic mypy plugin in C08, as planned.
3. Shutdown has no `try/finally`: if `dispose_redis()` raises, `dispose_engine()` is skipped. Unlikely with `aclose()`, but a `try/finally` would make the teardown order unconditional.
