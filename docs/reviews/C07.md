# C07 — infra.docker

## Contract
```
Purpose:    multi-stage Dockerfile + compose for api, worker, beat, postgres, redis,
            mock-crm, mailpit.
In -> Out:  `docker compose up` -> 7 healthy services within 60 s.
Errors:     image build fails -> build log shows the failing step.
Side fx:    creates volumes for postgres data.
Deps:       docker only (no python deps added).
```

**Deviation from the contract (agreed with the reviewer, recorded in LOOP.md):**
`celery==5.6.3` was added to `backend/requirements.txt` (the contract says
"Deps: docker only"), because worker/beat are real application code, not just
infrastructure; celery is on the AGENTS.md allow-list.

## Delivery note (written by the implementer)
_Exactly 5 points._

1. What it does: `backend/app/workers/` adds a real Celery app (`celery_app.py`: `Celery("integro")`, broker = `REDIS_URL` db 0, result backend = the same URL with the path switched to db 1, no new `Settings` fields) and a `ping() -> "pong"` task (`tasks.py`, no sleep placeholders). `infra/Dockerfile` is a multi-stage `python:3.13-slim` image (venv in /opt/venv, non-root uid 1000, CMD uvicorn) shared by three roles; `infra/mock-crm/` is a minimal FastAPI stub (GET /health, POST /leads -> 201 echo + id, in-memory). The root `compose.yaml` brings up exactly 7 services with no .env and no external keys.
2. Why it is built this way: the three roles (api/worker/beat) share the `integro-backend` image tag (each service declares `image:` + the same anchored `build:` so compose never tries to pull); broker and result backend derive from the single `REDIS_URL` by rewriting the URL path with `urllib.parse` — no new configuration; healthchecks avoid curl/wget in the app image — `python -c urllib` (api, mock-crm), `redis-cli ping`, `pg_isready`, busybox `wget` in mailpit (tag `axllent/mailpit:v1.33.0`; `/livez` verified empirically), worker — `inspect ping | grep -q pong`, beat — pidfile + `kill -0`.
3. How it is structured internally: `celery_app.py` reads `REDIS_URL` from the environment at import time (no connection is made); tasks register through `include=["app.workers.tasks"]` — without it the worker starts with an empty registry (caught on the live stand); the mock CRM keeps leads in process memory; compose uses `depends_on` with `service_healthy` for postgres/redis, and `SECRET_KEY: ${SECRET_KEY:-local-demo-only}` — a demo placeholder, commented as not a secret.
4. Where the traps / failure modes are: celery beat writes its scheduler db to the WORKDIR by default, which is root-owned after COPY — uid 1000 gets PermissionError; fixed with `-s /tmp/celerybeat-schedule` (do not switch USER to root); the worker healthcheck is honestly empty without a worker: `inspect ping` prints "No nodes replied" and exits 1 (verified by stopping the worker); the beat healthcheck exits 1 without a live pidfile (verified by moving it); celery ships no `py.typed` (verified) — exactly one `# type: ignore[import-untyped]` on the import line; a missing `REDIS_URL` now fails loudly at import (`os.environ["REDIS_URL"]`), with the test module providing the value via `os.environ.setdefault` before import; the live stand is always torn down by PID, never by process-name masks (lesson from the C06 incident).
5. How to verify it: a clean venv installed strictly from `backend/requirements.txt`: `ruff check .` clean, `mypy app` clean (15 files), `pytest -q` -> 39 passed (38 + the new include-registry guard). Live stand: `docker compose build` exit 0; `up -d --wait --wait-timeout 60` exit 0; `docker compose ps` -> 7/7 healthy; `GET :8000/health` 200, `GET :8000/ready` 200, `GET :8000/metrics` 200; e2e `ping.delay().get(timeout=10)` -> `pong`; `down -v` exit 0, no integro containers or volumes left. Secret scan: no gmail address anywhere in the repository; no old-project traces and no Cyrillic outside this review's quoted history; all C07 files are clean; `docker compose config` contains only demo values (integro/integro, local-demo-only).
